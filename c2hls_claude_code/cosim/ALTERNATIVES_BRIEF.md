# Brief: a fast RTL correctness check for autosa_mm kernels, while Vitis cosim runs in the background

Snapshot: 2026-10-10 04:40 PDT. Everything here was measured or checked in this workspace unless marked otherwise.

## 1. Goal

We have 13 HLS designs of `autosa_mm`: fp32 C = A·Bᵀ, I = J = K = 1024, AMD Alveo U280 (`xcu280-fsvh2892-2L-e`), 3.33 ns clock. All pass C simulation. We need to know whether their **generated RTL** computes the right C at the full 1024³ size.

There are two separate questions, answered by two separate tools:

| Question | Reference tool | Status |
|---|---|---|
| **Cycle count** of the RTL | **Vitis C/RTL cosim** (`cosim_design`). Its cycle counts are *the* reference numbers. | Running in the background; it takes days. **Leave it running.** |
| **Correctness**: are the RTL's output values right? | **Your task:** a much faster RTL simulation (Verilator) | To build |

**Your goal:** build a fast RTL simulation flow that runs the *same Vitis-HLS-generated RTL* on the full 1024³ bench and says PASS or FAIL against the bench's golden result.
- **It is for correctness only.** Its cycle count is *not* a reference number. Report it if you like, labelled "not reference".
- **Don't tune for cycle accuracy.** The real cycle counts come from the Vitis cosim runs; we compare those one-to-one later, when they finish.

## 2. Why Vitis cosim is not enough (measured)

**It's slow.**
- Setup (csynth, the C testbench run, `xelab` elaboration) takes 20–70 min per design.
- After **~30 hours** of simulation, none of the first 9 jobs has finished.

**Memory.** The cosims that ran with Vitis's dependence checker on grew without bound:
- `04_refined_v2_agent_r1` was killed at 128 GB, then again at 256 GB, with 5.7M+ warnings;
- `11_refined_v2_plain_r3` reached 126 GB of 128 GB, with 13.4M warnings, and was cancelled;
- `10` and `12` were growing past 70–90 GB and were cancelled as well.

The cause was the **DEPENDENCE-pragma checker**. With `-disable_dependency_check`, the jobs stay flat at 16–32 GB. Vitis cosim jobs now run with that flag, plus:
- `-trace_level none`;
- `xelab -mt off`, because default `xelab` segfaults (SIGSEGV, XSIM 43-3316) on these large designs;
- node-local `$SLURM_TMPDIR`;
- `ulimit -c 0`.

**Correctness signal worth knowing.** For `04` and `11`, the dependence checker reported millions of hits at `kernel.cpp:74`: the same address re-accessed at loop distances 1–15 inside a loop the pragma declares dependence-free. Their RTL may really compute wrong values, which C simulation can't catch. **Your RTL check must be able to catch exactly this kind of bug.**

| **New TAPA (rapidstream-tapa) Verilator mode** | Same idea with Verilator | Needs TAPA-compiled designs. Out of the box, Verilator can't read Vitis's floating-point IP, which is simulated from VHDL `floating_point_v7_1` / `xbip_*` models. The real blocker is the FP IP, not TAPA. |
| **LightningSim / LightningSimV2 / OmniSim** (Georgia Tech sharc-lab) | Trace-based: runs the HLS LLVM IR on the CPU and adds the HLS schedule's timing | **Doesn't simulate the RTL**, so it can't catch RTL bugs. Validated only with Vitis HLS 2021.1 (we use 2023.2). **Its AXI model doesn't match Vitis 2023.x** (see §3.1), so it would have to be fixed before its numbers mean anything for our designs. OmniSim's code isn't released. Not a correctness tool for our purpose. |

### 3.1 LightningSim and its AXI model on Vitis 2023.2: needs fixing

- **The problem.** LightningSim (github.com/sharc-lab/LightningSim, AGPL-3.0) models `m_axi` memory traffic with a model built from the **Vitis HLS 2021.1** AXI interface (`m_axi` adapter). The maintainers' docs say newer Vitis HLS versions have new AXI interface code with different performance behaviour, so simulations of newer-version designs can be significantly less accurate. They were reworking the model but hadn't released it. Their 99.9% cycle accuracy (33 benchmarks) holds only against 2021.1 cosim.
- **Why it matters here.** All our designs are memory-streaming kernels, with 512-bit `m_axi` ports, long bursts and many outstanding requests, generated by **Vitis HLS 2023.2**. Without a fix, LightningSim's latency and stall numbers for them would be unreliable.
- **What has to be fixed before using it.**
  1. **Update the AXI model to the 2023.2 `m_axi` adapter:** read/write request latency, burst splitting at `max_*_burst_length` and 4 KB boundaries, outstanding-transaction limits (`num_*_outstanding`), read/write data FIFO depths, and 512-bit widening (`max_widen_bitwidth`).
  2. **Check its parsers handle 2023.2 output:** the solution directory layout, the LLVM IR / `.adb` files, and the schedule reports.
  3. **Calibrate against Vitis 2023.2 cosim:** small designs first (the 16³ self-test kernels finish Vitis cosim in about a minute), then one full design once its Vitis cosim finishes.
- **What it would give once fixed.** Fast estimates of latency, stalls and deadlocks, plus the C-level functional output. It still **wouldn't check the RTL**, so it complements the Verilator correctness check (§4) and doesn't replace it. Vitis cosim remains the reference for cycle counts.
- **Priority.** Secondary to the Verilator correctness flow. Pursue it only if the user asks for a fast cycle-estimation path.
| **Commercial simulators** (VCS, Xcelium, Questa, Riviera) via `cosim_design -tool` | Faster event-driven simulators | Needs a license on the cluster. Availability unknown; ask the user before spending time on it. |

## 4. Recommended approach: Verilator on the Vitis-HLS RTL, with behavioural FP models

### 4.1 The obstacle and the fix
- **What the RTL contains:** Vitis HLS 2023.2 RTL (`hls_proj/sol1/syn/verilog/*.v`) is Verilog. But each floating-point operator is a small wrapper, for example:
  - `autosa_mm_fadd_32ns_32ns_32_7_full_dsp_1.v`;
  - inside it, a `*_ip.v` / `*_ip.tcl` instance of `floating_point_v7_1`, an encrypted VHDL core.
- **The fix:** replace each FP IP instance with a **behavioural Verilog/SystemVerilog model with the same ports, handshake (`aclk`, `aclken`, `s_axis_*_tvalid/tdata`, `m_axis_result_tvalid/tdata`) and latency**. The latency is in each wrapper's name and in its `.tcl` (`CONFIG.c_latency`).
- **The arithmetic:** single-precision add, multiply, etc., computed with `$bitstoshortreal`/`$shortrealtobits` or `real` and rounded to fp32, then delayed through a shift register of the IP's latency.

### 4.2 Numerical equivalence (why this is a valid correctness check)
- **Rounding:** the Xilinx FP IP rounds to nearest-even, so it matches IEEE-754 single precision.
  - **fmul:** the exact product of two 24-bit significands fits in a double, so double → fp32 rounding is exact.
  - **fadd via double:** this can differ by a double-rounding effect only in rare tie cases.
- **Denormals:** the IP flushes them to zero. The bench data (A and B uniform in [0,1]) produces no denormals in practice.
- **Tolerance:** the bench passes when |golden − C| ≤ 0.001, so tiny rounding differences can't flip a verdict. A wrong-dependence bug produces large errors.
- **Optional:** implement fp32 add and multiply bit-exactly in integer logic (for example a small Berkeley HardFloat-style module), then compare bit-for-bit with csim output too.

### 4.3 Flow to build (suggested)
1. **RTL.** csynth each kernel with c2hls `hls_eval.run_hls_synthesis` (the same settings as all our numbers: part `xcu280-fsvh2892-2L-e`, clock 3.33, `allow_compile_jobs=False`). Take `hls_proj/sol1/syn/verilog`.
2. **FP swap.** List every `*_ip` module instantiated (grep the wrappers), generate a behavioural model per op type and latency, and exclude the VHDL IP. Also handle any other Xilinx primitives the RTL instantiates.
3. **Testbench (C++ driving Verilator).** Model the top's `s_axi_control` (write A/B/C base addresses at the offsets listed in `autosa_mm_control_s_axi.v`, set `ap_start`, poll `ap_done`) and one simple AXI4 memory slave per `m_axi` bundle (`gmem0/1/2` = A/B/C, 512-bit data). The memory slave should support bursts, multiple outstanding transactions and `WSTRB`.
   - **Reference implementation:** `cosim/fastcosim/vendor/tapa_fast_cosim/templates.py` (`get_axi_ram_module`, `get_s_axi_control`, `get_dut`, `get_test_signals`).
   - **Bundle mapping:** `run_fast_cosim.py` shows how A/B/C map to bundles via the INTERFACE pragmas.
4. **Data and check.** Reproduce the bench **exactly**:
   - `rand()`: A row-major first, then B, each value `(float)rand()/RAND_MAX`;
   - C starts at zero;
   - golden = sequential fp32 accumulation over k;
   - an error is an element with |golden − C| > 0.001;
   - `static_assert` I = J = K = 1024.
   
   `cosim/fastcosim/gen_data.cpp` already does all of this; reuse it.
5. **Build options.** `verilator --cc --exe --build -O3 --x-assign fast --x-initial fast`, with `--threads N` worth trying. No tracing.
6. **Early stop.** Compare each C beat as it is written, and stop on the first mismatch. Add a stall watchdog (no C write for many cycles) to catch deadlocks.

### 4.4 Validation (mandatory before trusting it)
1. **16³ self-tests**, with `kernel.h` sizes changed for the test only:
   - the naive kernel must pass;
   - a kernel with one wrong element must fail.
   
   Reuse `cosim/selftest/good_bundles.cpp` and `bad_bundles.cpp`.
2. **Cross-check against Vitis cosim** on at least one design once a Vitis cosim finishes: same verdict. Compare cycles too, for information only.
3. **Plausibility of cycle counts:** Verilator's count should be close to csynth's latency, as fast cosim was within +17 cycles at 16³. A large gap points to a testbench or model bug. It still isn't the reference.
