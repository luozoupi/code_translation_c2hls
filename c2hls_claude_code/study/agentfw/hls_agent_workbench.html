HLS Agent Workbench

A general agentic flow for HLS: Claude Code gets a goal, a workspace and one tool that runs real Vitis csim and csynth. There is no recipe, no fixed prompt sequence and no step order. The agent decides what to read, what to build, what to measure and when it is done.

This is separate from c2hls and HLSmith. The c2hls flows send fixed prompts and judge each reply; here the only fixed parts are the brief, the tool and the finish criteria.

The loop

One headless Claude Code session runs on a login node. It edits kernel.cpp, submits it through bin/hls, and reads back what Vitis reports. Every csim and csynth runs as its own Slurm job on a compute node, so the agent can run several experiments at once and keep thinking while they run.

The session ends when the agent stops on its own (best design left in kernel.cpp, findings in REPORT.md) or when the wall-time cap (10 h) is reached. A session stopped by a Claude usage limit is resumed with RESUME=1, which continues the same conversation.

What the agent is given

The brief

CLAUDE.md

Goal only: write the kernel.cpp with the lowest worst-case csynth latency that

  • passes csim on the fixed bench (outputs pre-filled with garbage, so read-modify-write fails);
  • synthesizes with every resource below 100% of the U280;
  • keeps the exact top signature.

No architecture hints and no resource target. It ends with what to leave behind: the design and a report.

The task

Workspace files

  • task.json: kernel, top, part, clock, pass and fail patterns
  • plain.cpp: the reference implementation
  • kernel.h, testbench.cpp
  • bin/: the tool, copied in (not linked)
  • knowledge/: only for know and team

Tasks so far: mm1024 (C = A·BT, 1024³ fp32) and lud32.

The rules

Permissions

  • Vitis and g++ only through bin/hls; the shell is otherwise read-only (ls, cat, grep, sed -n, awk, diff).
  • One command per shell call, no pipes or chaining, so the allow-list can be checked.
  • No MCP servers, no user settings, no slash commands; edits auto-accepted inside the workspace.

The one tool: bin/hls

Everything the agent learns about hardware comes through these six commands. Each submit snapshots the current kernel.cpp into its own experiment folder, so a result always belongs to the exact source that produced it.

CommandWhat it does
hls submit csim --tag NAMECopies kernel.cpp to exp/NAME/ and submits a Slurm csim on the task's testbench. Prints the job id.
hls submit csynth --tag NAMESame, for Vitis HLS csynth on xcu280 at 3.33 ns. Several jobs can run at once.
hls wait JOBBlocks up to 9 minutes and prints the job state. On a timeout it resubmits at the next tier (1 h, 3 h, 6 h).
hls result NAMEThe csim verdict (correct=True or Failed with N errors) or the csynth summary: best and worst latency, II, DSP, LUT, FF, BRAM, URAM, per-loop bottlenecks.
hls diag NAMERuns the DATAFLOW diagnostic on the module-level reports: do load, compute and store really overlap, and which stage sets the pace.
hls floor DSPCompute floor for a DSP count: total multiply-adds / (DSP / 5). Lets the agent see how far a design is from its own limit.

One real run, step by step

The base variant on mm1024, 13 October (times PDT). Every step below is from exp/log.jsonl and the agent's own REPORT.md. Bars show worst-case latency against the first full design.

  2. 15:11v1_ti16First architecture at 16 rows, only to check the loop reaches II=1.4,195,475 cycles
  3. 15:14v1_ti103 + csim103 rows × 16 lanes, default operators (5 DSP per multiply-add). First correct full design.

    532,739 · 113% DSP · rejected

Resumed, it read its finished jobs, kept v4_ti171_f7 and wrote REPORT.md, including why it stopped: latency only drops in whole 65,536-cycle blocks, and 5 blocks would need about 3,280 multiply-adds, beyond the DSP and LUT left.57 s

9 csynths and 5 csims, 2.2 hours of active session, $7.14 in total. 404,451 cycles is 2.6 times faster than AutoSA st0_c6 (1,054,811 worst case).

What to keep in mind about this result

It is a csynth estimate. Two DEPENDENCE false pragmas are argued from index analysis but cannot be checked by csim, so cosim should confirm them. At 95% DSP and 87% LUT the design is unlikely to place and route at 300 MHz. And it is one run.
