The testbench now checks C = A·BT with C poisoned

AutoSA's kernel computes C = A·BT and overwrites C. The original c2hls bench wrote plain.cpp as C = C + A·B, but its testbench never set C before the call, so a kernel that read C and one that overwrote it both passed. The fixed bench (study/bench_fixed/) fills C with 12345.0 before the call and checks every one of the 1,048,576 outputs. Every result from 13 October on uses it.

Compute floor

The fewest cycles a design could take with its DSP count, if every multiply-add unit started a new operation each cycle.

floor = 1024³ / (DSP / 5)

fp32 multiply-add ≈ 5 DSP. “× floor” = cycles / floor; 1.0× is perfect.

Reaching 1M cycles

Needs about 1,070 multiply-adds per cycle, which is about 5,400 DSP. AutoSA's 128 PE × SIMD 8 systolic array (config st0_c6) has 1,024: 1,048,845 cycles best case and 1,054,811 worst case.

What the numbers are

Vitis HLS csynth estimates. Percentages are of the whole U280: 9,024 DSP, 1,303,680 LUT, 4,032 BRAM_18K, 960 URAM, 2,607,360 FF. The ladder's csim column is the old bench; sections marked “fixed bench” check C = A·BT with C poisoned.

HLSmith-SingleStep-Refined-Expertise (Refined skills)

What changes: Swaps Expertise for Refined-Expertise: the hold-back cues are removed from the prompts and skills, and the balance gate is added (see “What refined means” below). Nothing asks for DSP, in words or by a gate.

With the hold-back wording gone and the balance gate on, but still no DSP asked for, both models grow on their own. Opus reaches 2,672 to 5,248 DSP and 1.18M to 2.36M cycles, within 1.16 to 1.24 times its compute floor. DeepSeek reaches 672 to 1,600 DSP and 2.75M to 8.81M cycles. Where the cycles go

Adding DSP only shortens the compute phase. Each design's csynth latency was split into loading A, B and C, computing, and storing C, using every loop's csynth latency times the number of times it runs; the parts add back up to the reported latency within 0.4% for all 35 designs. Three things keep latency from falling as DSP grows.

load A, B, Ccompute store Cother DATAFLOW designs show each stage instead; stages run at the same time and the longest one sets the latency.
  1. Loads and stores that never overlap compute. Opus's filled refined designs (8,192 to 8,326 DSP) spend 71 to 77% of their time computing at about 2,000 multiply-adds per cycle, but the other 23 to 29% is B preload and per-tile load and store, done one after another. Doubling DSP would halve only the compute part. The refined designs with the requirement in words (5,120 DSP) compute at exactly 1,024 multiply-adds per cycle, their floor, for 80 to 84% of the time; serial loads are the rest.
  2. Memory loops that move one float per cycle. A 512-bit port can carry 16 floats per cycle, but a loop that reads a plain float array runs at II=16. In Opus's DSP-floor r1 (8,320 DSP, 2.85M cycles), loading and storing C this way takes 75% of the latency; compute is 23%. In window r1, DATAFLOW overlaps everything, but the A loader runs at II=16 and sets the pace at 1.06M while compute needs only 0.79M.
  3. Compute loops that cannot start every cycle. Adding into the same fp32 accumulator every cycle forces II=4 or more, so DSPs sit idle. DeepSeek's refined designs unroll about 1,024 multiply-adds, but the loop runs at II=4, so they finish only about 255 per cycle and three quarters of that hardware waits at any moment. Its zero-shot designs run one serial add chain at II=64: a quarter of a multiply-add per cycle.

The agentic L2 design avoids all three: five DATAFLOW stages with a ping-pong B buffer, and its compute stage is 98.4% of the latency at exactly 1,024 multiply-adds per cycle. That is why it lands next to AutoSA st0_c6.

Two worst-case numbers are pessimistic. Refined-in-words r3 charges its A load on all 64 tiles but runs it on 8 (true latency about 1.27M, not 1.73M); refined + floor r2 counts its one-time B load twice (about 820K, not 852K). Separately, the testbench checks C = A·BT and never sets C beforehand, so a design may either read C and add to it (as plain.cpp is written) or overwrite it. Eight DeepSeek designs overwrite C and so skip the C load that Opus's designs pay for; both pass strict csim.

Why DeepSeek's large designs never finish

DeepSeek's stalled designs (9 of them)

  • One flat function, no DATAFLOW.
  • One pipelined loop fully unrolled into 5,600 to 9,000 fp32 multiply-adds, every accumulator its own register.
  • Vitis reports 23K to 125K instructions before scheduling, then spends 5+ hours on that one loop until Slurm stops it.
  • In 5 of 9, the accumulator is read and written back to back, so Vitis keeps retrying slower schedules.

Opus's high-DSP designs that pass

  • Load, compute and store as separate DATAFLOW stages, or a moderate grid with explicit adder trees.
  • Each accumulator reused only every 16 to 64 cycles.
  • 13K to 29K instructions; csynth takes 1.5 to 20 minutes.
  • Opus is not immune: its one bare-floor failure was a 167K-instruction grid with no DATAFLOW.

HLSmith-Agentic-Refined-Expertise + Resource-Window (Agentic ladder L2: the 5,152-DSP design)

The controlled runs above give Opus no tools: it answers each prompt with code, exactly like DeepSeek. An earlier Claude-only campaign also ran the same c2hls flow in agent mode, and its stage-2 design is the one at 5,152 DSP.

The DSP ladder

Three flash runs in a row, each seeded with the previous stage's kernel, using the refined prompts, refined v2 skills, balance gate and a DSP window as floor plus cap. Stage 1 asks for about 25% of the DSP. Stage 2 says: double the parallel MACs, keep the architecture, scale buffering and bandwidth with it, and be faster. Stage 3 grows toward the 80% roof.

Agent mode

When c2hls sends a flash or repair prompt, Claude Code runs in a workspace holding kernel.cpp, kernel.h and the testbench. It can read and edit files and run one script, ./hls_check.sh compile|csim|csynth, which runs real Vitis HLS on a compute node (12 checks per session). It can test a design before answering. Plain mode cannot.

How the L2 design was made

  1. Stage 1 produced a correct design at 2,592 DSP and 2.11M cycles.
  2. Stage 2's first two calls hit Claude's session limit. The shim then returned the unchanged stage-1 kernel, which the DSP window rejected as too small. (That shim bug is fixed; it returns an error now.)
  3. The rejection prompt started a real 71-minute agent session. Opus read the kernel, doubled the PE rows (16 to 32) and the row tile (32 to 64) with seven edits, ran csim (passed), then csynth (1,066,083 cycles, 5,152 DSP), and returned it. It used 2 of its 12 checks.

5,152 DSP is 1,024 fp32 multiply-adds (5,120 DSP) plus 32 DSP of index arithmetic: the same MAC count as AutoSA's 128 × 8 array. At 1,066,083 cycles (best and worst case are equal) it runs within 1.02× of its compute floor. That is within 1.1% of AutoSA st0_c6's worst case (1,054,811) and 1.6% above its best case (1,048,845), with headroom left on every resource.

Is it really DATAFLOW? A diagnostic that reads Vitis, not the pragma

A #pragma HLS DATAFLOW line proves nothing. study/dfdiag/dfdiag.py reads what Vitis actually built: the “Applying dataflow … extracted N process” and “Implementing PIPO” log lines, each module's csynth report, and the loop tables. It then checks whether stages overlap: a dataflow loop of N iterations with latency close to N·II + (L − II) is overlapping; one close to N·L is not. It also flags transfer loops at II > 1, compute loops at II > 1, serial work outside the region, and a non-compute bottleneck stage.

LUD: AutoSA's design space, then the same ablation

What AutoSA offers

AutoSA ships one LU recipe (space_time 3, no tiling) and no U280 model. Its paper reports LU only for N = 12 to 24 on a U250, from RTL simulation at 250 MHz, with no resources. Because LU cannot be tiled in AutoSA, the whole design space is N × space_time. All 30 points were generated at AutoSA rev b61a1b4 and run through Vitis 2023.2 csim and csynth for xcu280 at 3.33 ns.

What we found

  • space_time 0, 1 and 3 compute U wrong at every N: each row of U is shifted one column, while L is exact. Checked against a numpy LU. This includes the README recipe; regenerating without --hls gives the same kernel.
  • space_time 2 passes csim but fails csynth: an internal stream is not produced and consumed exactly once.
  • space_time 4 and 5 are correct; their csynth takes hours at large N.
  • AutoSA's own LU testbench compares L only where the algorithm never writes it; our bench checks the real L and U with both poisoned.
