# Space-time 0, candidate 1

Instruction for one AutoSA 1024³ U280 matrix-multiply design:

```text
kernel[]->space_time[0];kernel[]->array_part[128,128,8];kernel[]->latency[1,32];kernel[]->simd[8]
```

The schedule below is taken from the generated kernel at `artifacts/dse/campaigns/20260927_mm1024_u280_st0/u280_paper/validation/mm1024/candidate_1/autosa_out/src/kernel_kernel.cpp`, so the loops, buffers, and streams can be reconstructed without opening that file. Module wiring that is shared by every space-time 0 design is explained once in [stream_stitching.md](../stream_stitching.md).

## 1. Identity

- **Space time:** 0. Space loops: `i`. Time loops: `j` and `k`.
- **array_part:** 128, 128, 8. Axis order for this space time is `i, j, k`. `array_part[t]` is the tile of axis `t` in that order. Loops outside the tile run `1024 / array_part[t]` times.
- **latency:** 1, 32. One factor per coincident loop, which for this GEMM are `i` and `j`. `k` is the reduction and is not a latency factor.
- **SIMD:** 8.
- **PE array:** `array_part[0] / latency[0]` = 128/1 = **128**. The array is 1-D: `p0` = 0..127. There is no `p1`.
- **Problem:** `I = J = K = 1024`. The kernel statement is `C[i][j] = C[i][j] + A[i][k] * B[j][k]`. The printed statement is `S_0(i, j, k)`.
- **Campaign:** `artifacts/dse/campaigns/20260927_mm1024_u280_st0/u280_paper/validation/mm1024/candidate_1/`. Part folder `u280_paper` (Alveo U280). This is candidate `1` of space-time 0. The same `(space_time, array_part, latency, simd)` tuple is recorded 3 times in `artifacts/dse/mm1024_u280_three_rankings.csv` (the hls-min, hls-max, and model rankings).
- **Generated kernel:** present. `artifacts/dse/campaigns/20260927_mm1024_u280_st0/u280_paper/validation/mm1024/candidate_1/autosa_out/src/kernel_kernel.cpp`, header `artifacts/dse/campaigns/20260927_mm1024_u280_st0/u280_paper/validation/mm1024/candidate_1/autosa_out/src/kernel_kernel.h`, schedule `artifacts/dse/campaigns/20260927_mm1024_u280_st0/u280_paper/validation/mm1024/candidate_1/autosa_out/latency_est/PE_loop_info.json`.
- **Flags:** The campaign command uses `--host-serialize --hls --tuning-method=0`. `array_part_L2` and HBM are off. Two-level buffering is off because `--host-serialize` is on. No kernel in this campaign contains a credit FIFO. This space time is compiled without `--local-reduce` and without `--simd-touch-space`.

Data types printed in the header:

typedef float B_t1;

typedef ap_uint<512> A_t16;
typedef ap_uint<256> A_t8;

## 2. Loop order

The space loop is `i`, and it is not a C loop inside `PE`. It is the module id `p0`. Every loop below is time: the `j` and `k` tiles, plus the latency point of any space axis that was divided across PEs.

Nest from `PE_loop_info.json`, outer loop first. A mark applies to the loop that contains it.

| Step | What | Range | Role |
|---:|---|---|---|
| 1 | `p0` | 0..127 | Space index along `i`. Its coefficient is `latency[0]` = 1, so PE `p0` and PE `p0+1` own `i` values 1 apart. |
| 2 | `c0` | 0..7 (trip 8) | Temporal tile of `i`. Trip 8 = 1024/128. |
| 3 | `c1` | 0..7 (trip 8) | Temporal tile of `j`. Trip 8 = 1024/128. |
| 4 | `c2` | 0..127 (trip 128) | Temporal tile of `k`. Trip 128 = 1024/8. |
| 5 | `c4` | 0..3 (trip 4) | Latency strip of `j`. The tile of 128 is split into 4 = 128/32 strips of 32. |
| 6 | `c6` | 0..31 (trip 32) | Latency point of `j`. Trip 32 = `latency[1]`. It sits under a `latency` mark. |
| 7 | `c7` | 0..7 (trip 8) | SIMD unroll of `k`. Trip 8 = `simd` 8. The schedule marks it `simd` / `hls_unroll`, and the kernel prints `#pragma HLS UNROLL` on this loop. |

## 3. What each factor does to `i`, `j`, and `k`

The printed statement, from `PE_loop_info.json`, is:

```text
S_0(p0 + 128 * c0, 128 * c1 + 32 * c4 + c6, 8 * c2 + c7)
```

- `i = p0 + 128 * c0`
- `j = 128 * c1 + 32 * c4 + c6`
- `k = 8 * c2 + c7`

`array_part` is stored in order `i, j, k`, so 128, 128, 8 are the tiles of `i`, `j`, and `k`.

### i

Expression: `p0 + 128 * c0`.

- `1 * p0` — Space index along `i`. Its coefficient is `latency[0]` = 1, so PE `p0` and PE `p0+1` own `i` values 1 apart.
- `128 * c0` — Temporal tile of `i`. Trip 8 = 1024/128.

### j

Expression: `128 * c1 + 32 * c4 + c6`.

- `128 * c1` — Temporal tile of `j`. Trip 8 = 1024/128.
- `32 * c4` — Latency strip of `j`. The tile of 128 is split into 4 = 128/32 strips of 32.
- `1 * c6` — Latency point of `j`. Trip 32 = `latency[1]`. It sits under a `latency` mark.

### k

Expression: `8 * c2 + c7`.

- `8 * c2` — Temporal tile of `k`. Trip 128 = 1024/8.
- `1 * c7` — SIMD unroll of `k`. Trip 8 = `simd` 8. The schedule marks it `simd` / `hls_unroll`, and the kernel prints `#pragma HLS UNROLL` on this loop.

Factors that do not grow an extra loop on this config:

- `latency[0]` = 1 is skipped. The kernel emits no `i` point loop. `p0` already selects a single `i` inside the tile, and the PE count uses `128/1`.
- The `k` tile equals the SIMD factor 8, so there is no extra group loop between the tile and the unroll. One tile is one unrolled vector.

A few concrete index tuples from that expression (PE 0 unless the row says otherwise):

| Point | i | j | k |
|---|---:|---:|---:|
| PE 0, every iterator 0 | 0 | 0 | 0 |
| last SIMD lane `c7` = 7, other iterators 0 | 0 | 0 | 7 |
| last pipelined step `c6` = 31, other iterators 0 | 0 | 31 | 0 |
| PE 0, every loop at its upper bound | 896 | 1023 | 1023 |
| last PE 127, every loop at its upper bound | 1023 | 1023 | 1023 |

Host transfer order, from the header. This is the same tiling, written as subscripts of the original matrices:

```c
/* host_serialize_A */ A_to[cnt++] = A_from[(128 * c0 + c3) * 1024 + (8 * c2 + c5)];
/* host_serialize_B */ B_to[cnt++] = B_from[(128 * c1 + c3) * 1024 + (8 * c2 + c4)];
/* host_deserialize_C */ C_to[(128 * c0 + c3) * 1024 + (128 * c1 + c5)] = C_from[cnt++];
```

## 4. PE array

`PE` takes `int idx` and sets `p0 = idx`. `kernel0` instantiates `p0` = 0..127.

For a fixed tile, PE `p0` owns `i = p0 + 128 * c0` with the `i` point running through its latency extent (1 value). Across `i` tiles it revisits the same offset in every tile of 128. It owns every `j` of the `j` tile `128` (the whole time axis that stays live in `local_C`), and it reduces every `k` into that tile. A is the vector `A[i][k]` for that one `i` beat. B is `B[j][k]` for the current `j`, consumed from the previous PE along `i` and forwarded to the next.

`kernel0` contains 128 `PE_wrapper` calls, one per PE, matching the formula above.

The first PE call, and the next one along the forwarding direction:

```text
PE_wrapper(0, fifo_A_PE_0, fifo_B_PE_0, fifo_B_PE_1, fifo_C_drain_PE_0)
PE_wrapper(1, fifo_A_PE_1, fifo_B_PE_1, fifo_B_PE_2, fifo_C_drain_PE_1)
PE_wrapper(127, fifo_A_PE_127, fifo_B_PE_127, fifo_B_PE_128, fifo_C_drain_PE_127)
```

## 5. Local buffers

Declared in `PE`:

```c
A_t1 local_A[1][8];
#pragma HLS ARRAY_PARTITION variable=local_A dim=0 complete
B_t1 local_B[1][8];
#pragma HLS ARRAY_PARTITION variable=local_B dim=0 complete
C_t1 local_C[1][128];
#pragma HLS RESOURCE variable=local_C core=RAM_2P_BRAM
```

`local_A[1][8]` and `local_B[1][8]` are one FIFO beat. The second dimension is the SIMD factor that the kernel actually unrolls. Both are `#pragma HLS ARRAY_PARTITION dim=0 complete`. The first dimension stays 1 because a beat is consumed on the pipelined iteration and is not stored across `i` or `j` points.

`local_C[1][128]` is the `C` this PE owns. The first extent is `latency[0]` = 1 (the `i` points left on the PE). The second extent is the full `j` tile 128, because `j` is time and those values stay live across `k`. Space-time 0 does not run array contraction: the campaign does not pass `--local-reduce`. The kernel maps it with `RAM_2P_BRAM`.

The MAC writes:

```c
local_C[0][32*c4 + c6] = (local_C[0][32*c4 + c6] + (local_A[0][c7] * local_B[0][c7]));
```

The subscripts are the `i` point (constant 0 when `latency[0]` is 1) and the offset of the current `j` inside the tile.

IO buffers are separate from the PE arrays. They are quoted in the module table below. Load modules that double-buffer declare `local_*_ping` and `local_*_pong` and alternate `inter_trans` / `intra_trans` on them. That pair is the default double buffer. It is not the `--two-level-buffer` flag, which this campaign leaves off.

## 6. Load and store modules

Every `kernel0` argument is a 512-bit word. The header typedefs are `ap_uint<512> A_t16`, `B_t16`, and `C_t16`. That width is the outer data-pack (16 floats, the 64-byte default). It is not a field of `sa_sizes`. The interior streams on this config are narrower where the file says so.

Serialize modules in this kernel:

- `void A_IO_L2_in_serialize(A_t16 *A, hls::stream<A_t8> &fifo_A_local_out)` — reads DRAM. Loops: `i` = 0 .. 524287 (trip 524288), `p` = 0 .. 1 (trip 2). Shift: >> 256.
- `void B_IO_L2_in_boundary_serialize(B_t16 *B, hls::stream<B_t8> &fifo_B_local_out)` — reads DRAM. Loops: `i` = 0 .. 524287 (trip 524288), `p` = 0 .. 1 (trip 2). Shift: >> 256.
- `void C_drain_IO_L2_out_serialize(C_t16 *C, hls::stream<C_t4> &fifo_C_drain_local_in)` — writes DRAM. Loops: `i` = 0 .. 65535 (trip 65536), `p` = 0 .. 3 (trip 4). Shift: no shift.

The PE signature is `void PE(int idx, hls::stream<A_t8> &fifo_A_in, hls::stream<B_t8> &fifo_B_in, hls::stream<B_t8> &fifo_B_out, hls::stream<float> &fifo_C_drain_out)`.

A's serialize stream and the PE port are the same type, `A_t8` (`ap_uint<256>`, 8 floats). The 512-bit DRAM word is split in `A_IO_L2_in_serialize` down to that width.
B's serialize stream and the PE port are the same type, `B_t8` (`ap_uint<256>`, 8 floats). The 512-bit DRAM word is split in `B_IO_L2_in_boundary_serialize` down to that width.

At the PE, A and B use `A_t8` / `B_t8` (`ap_uint<256>`, 8 floats). `local_A` and `local_B` are `[1][8]` scalars (`A_t1` / `B_t1`, which are `float`), fully partitioned.
The unpack loop shifts the FIFO word by 32 bits once per lane and is unrolled 8 times.

C leaves the PE as `hls::stream<float>`. The drain modules pack four floats into `C_t4` (`ap_uint<128>`). `C_drain_IO_L*_out_serialize` concatenates four `C_t4` beats into one `C_t16` store (`p < 4`). The store trip is 65536 words of 16 floats, which is the full 1024×1024 `C`.

Counting floats through the 512-bit port: A is read 8 times (once per `j` tile, 1024/128) and B is read 8 times (once per `i` tile, 1024/128). Inside an `i` tile, B is forwarded from PE to PE, so each `p0` reuses the beat that entered at `p0` = 0. Inside a `j` tile, the A IO chain delivers each PE its own A beats.

Every top-level module in this kernel (wrappers and the `intra_trans` / `inter_trans` helpers omitted). Call counts are the instantiations in `kernel0`. A boundary module is the end of a chain and has no forward port.

| `A_IO_L2_in_serialize` | 1 | — | — |
| `A_IO_L1_in` | 127 | `A_t8 local_A_ping[1][1];`<br>`A_t8 local_A_pong[1][1];` | `c0` 0..7 (trip 8), `c1` 0..7 (trip 8), `c2` 0..127 (trip 128) |

A is loaded by `A_IO_L2_in_serialize` → `A_IO_L2_in` → an `A_IO_L1_in` chain with one module per PE. The last PE's module is `A_IO_L1_in_boundary`. B is loaded by `B_IO_L2_in_boundary_serialize` → `B_IO_L2_in_boundary`, which feeds `PE(0)` only; later PEs get B from their neighbor. C is stored by the `C_drain_IO_L1_out` chain (boundary at the highest `p0`), then `C_drain_IO_L2_out`, then `C_drain_IO_L2_out_serialize`. Names stay `C_drain_*` because C is finished inside the PE and then drained.

## 7. Streams

All of the following are `hls::stream` channels declared in `kernel0`. Every one is `#pragma HLS STREAM ... depth=2`. Depth 2 is the generator default for this campaign. The tile sizes change how many beats are pushed, not the FIFO depth. A full FIFO stalls the producer. An empty FIFO stalls the consumer. The DRAM-edge serialize channels do not carry `core=FIFO_SRL`. Every PE and IO-chain channel does.

There is no credit FIFO in this file.

| FIFO family | Count | Element | Depth | Pragma | What moves |
|---|---:|---|---:|---|---|
| `fifo_A_A_IO_L2_in_serialize` | 1 | `A_t8` (`ap_uint<256>`, 8 floats) | 2 | no `FIFO_SRL` (DRAM-edge serialize) | A feed, DRAM edge. `A_IO_L2_in_serialize` produces, `A_IO_L2_in` consumes. No `FIFO_SRL`. |
| `fifo_B_B_IO_L2_in_serialize` | 1 | `B_t8` (`ap_uint<256>`, 8 floats) | 2 | no `FIFO_SRL` (DRAM-edge serialize) | B load, DRAM edge. `B_IO_L2_in_boundary_serialize` produces, `B_IO_L2_in_boundary` consumes. No `FIFO_SRL`. |
| `fifo_C_drain_C_drain_IO_L2_out_serialize` | 1 | `C_t4` (`ap_uint<128>`, 4 floats) | 2 | no `FIFO_SRL` (DRAM-edge serialize) | C drain, DRAM edge. `C_drain_IO_L2_out` produces packed words, `C_drain_IO_L2_out_serialize` consumes them and writes `C_t16`. No `FIFO_SRL`. |
| `fifo_A_A_IO_L1_in` | 129 | `A_t8` (`ap_uint<256>`, 8 floats) | 2 | `FIFO_SRL` | A feed along the 1-D IO chain, increasing `p0`. `A_IO_L2_in` writes index 0. Each `A_IO_L1_in` reads its index and writes the next. The last index feeds the boundary module. |
| `fifo_A_PE` | 128 | `A_t8` (`ap_uint<256>`, 8 floats) | 2 | `FIFO_SRL` | A tap into the PE. `A_IO_L1_in(p0)` produces `fifo_A_PE_p0`. `PE(p0)` consumes it and has no `fifo_A_out`. |
| `fifo_B_PE` | 129 | `B_t8` (`ap_uint<256>`, 8 floats) | 2 | `FIFO_SRL` | B reuse along `i`. `B_IO_L2_in_boundary` produces `fifo_B_PE_0`. `PE(p0)` reads `fifo_B_PE_p0` and writes `fifo_B_PE_{p0+1}`. `B_PE_dummy_in` consumes the tail. |

## 8. Pipeline and unroll

The printed pipeline target is `#pragma HLS PIPELINE II=1`. It sits on the innermost loop under the `latency` / `hls_pipeline` mark.
On this config that loop is `c6` = 0..31 (trip 32). Latency point of `j`. Trip 32 = `latency[1]`. It sits under a `latency` mark.
The unrolled loop is `c7` = 0..7 (trip 8), marked `simd` / `hls_unroll`. SIMD unroll of `k`. Trip 8 = `simd` 8. The schedule marks it `simd` / `hls_unroll`, and the kernel prints `#pragma HLS UNROLL` on this loop.
The loops that shift the packed A and B words into `local_A` / `local_B` are also `#pragma HLS UNROLL`, with trip count 8.

The C update guard printed in `PE` is:

```c
if (c2 == 127)
fifo_C_drain_out.write(local_C[0][32*c4 + c6]);
```

The drain write fires on the last `k` iteration only. Until that iteration the PE only updates `local_C`. There is no `fifo_C_in` on this PE.

MAC statement:

```c
local_C[0][32*c4 + c6] = (local_C[0][32*c4 + c6] + (local_A[0][c7] * local_B[0][c7]));
```

## 9. How to read the generated kernel

Open `artifacts/dse/campaigns/20260927_mm1024_u280_st0/u280_paper/validation/mm1024/candidate_1/autosa_out/src/kernel_kernel.h` first. Read the typedefs, then `host_serialize_A`, `host_serialize_B`, and `host_deserialize_C`. Those three functions are the DRAM order.

Open `artifacts/dse/campaigns/20260927_mm1024_u280_st0/u280_paper/validation/mm1024/candidate_1/autosa_out/latency_est/PE_loop_info.json` and read it top to bottom. The `user_expr` that starts with `S_0` is the statement. Marks named `latency`, `hls_pipeline`, `simd`, and `hls_unroll` are the pipeline and unroll.

In `artifacts/dse/campaigns/20260927_mm1024_u280_st0/u280_paper/validation/mm1024/candidate_1/autosa_out/src/kernel_kernel.cpp`, the module bodies appear in this order. Wrappers are one-line callers and can be skipped. `*_intra_trans` and `*_inter_trans` are the two halves of a buffered IO module: `inter_trans` filters the chain, `intra_trans` moves the kept word to the next FIFO.

1. `A_IO_L2_in`
2. `A_IO_L2_in_serialize`
3. `A_IO_L1_in`
4. `A_IO_L1_in_boundary`
5. `B_IO_L2_in_boundary`
6. `B_IO_L2_in_boundary_serialize`
7. `PE`
8. `B_PE_dummy_in`
9. `C_drain_IO_L1_out`
10. `C_drain_IO_L1_out_boundary`
11. `C_drain_IO_L2_out`
12. `C_drain_IO_L2_out_serialize`

`kernel0` is last. It is one `#pragma HLS DATAFLOW` region: the FIFOs are declared, then one call per hardware instance. There is no C `for` over PEs.

`PE(int idx)` uses `p0 = idx`. Follow `fifo_A_PE_{p0}`, `fifo_B_PE_{p0}` into that PE, and `fifo_B_PE_{p0+1}` out. `fifo_C_drain_PE_{p0}` is the drain.

The cross-config picture of who produces each FIFO, and how A, B, and C differ across space times 0, 3, and 4, is in [stream_stitching.md](../stream_stitching.md). The campaign-wide rules for these factors are in [mm_codegen_factors.md](../../mm_codegen_factors.md).
