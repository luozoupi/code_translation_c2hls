## Impact: Dynamic Routing vs. Static Order on a Real External Kernel

To make the Phase 2 changes concrete, we replay the bottleneck signature observed by the Phase 1 end-to-end run on the [adapted CollectiveHLS knn](../external_datasets/CollectiveHLS/Applications/RodiniaHLS-KNN-Pipeline/knn.cpp) kernel (the same kernel that was synthesized through Vitis HLS 2025.2 in the Phase 1 artifact). Vitis HLS reported: 1 `interval_exceeds_latency` (high), 1 `non_pipelined_hot_loop` (high), and 4 `ii_target_miss` (medium).

| iter | Static order (current production) | Dynamic routing (Phase 2) |
|------|-----------------------------------|---------------------------|
| 1 | `tiling` (always first) | **`coalescing`** — matched `interval_exceeds_latency` → skill `prompt-coalescing` |
| 2 | `pipeline` | **`doublebuffer`** — matched `interval_exceeds_latency` → skill `prompt-doublebuffer` |
| 3 | `unroll` | **`tiling`** — matched `interval_exceeds_latency` → skill `prompt-tiling` |
| 4 | `doublebuffer` | **`pipeline`** — matched `non_pipelined_hot_loop` → skill `prompt-pipeline` |
| 5 | `coalescing` | **`unroll`** — matched `non_pipelined_hot_loop` → skill `prompt-unroll` |

The dynamic router prioritizes the **dominant** bottleneck (interval-exceeds-latency at the kernel boundary) over the canonical textbook progression. This is the "profile first, then fix" alignment promised in the plan. The same hooks that make this routing possible (Pillar 1 feedback + Pillar 3 skill library + Pillar 5 router + Pillar 9 collapse / throughput / rollback guards) also feed the Pillar 7 absorbed-by-Vitis Avoid band and the Pillar 4 candidate cache — all green in the checks above.
