# External Dataset Compatibility Survey

Generated by `dataset_pipeline.external_adapter.survey_dataset`. Each row counts C/C++ source files in the cloned repo, by their compatibility class with the c2hls plain.cpp input shape.

Class definitions:
- `clean_c` — file is already pragma-free and ap_uint-free; drop-in compatible after wrapping into a c2hls bench dir.
- `hls_pragmas` — file contains `#pragma HLS` / `#pragma ACCEL` lines; needs `_strip_hls_constructs()` before use.
- `hls_apuint` — uses `ap_uint<…>` types; needs the same stripper plus type rewriting before plain-C use.
- `hls_mars` — uses MARS_WIDE_BUS / memcpy_wide_bus helpers; stripper handles those too.
- `testbench` — name flagged as testbench (tb / test_ prefix); kept as-is for csim, not used as plain.cpp.

**Smoke checks on adapted `plain.cpp`**:

- contains `#pragma HLS`: **False** (expect False)

The adapted bench dir is still usable by Vitis HLS (which has its own header search path) — `g++` is just a cheap pre-flight, not a hard gate.

## End-to-end Vitis HLS synthesis on adapted external kernel

To prove Phase 1 is content-agnostic, the adapted `external_knn` was synthesized with Vitis HLS 2025.2 on `xc7a100t-csg324-1` at 4 ns clock. The full v1 metrics + v2 `feedback` dict landed:

**Top-level metrics (v1, unchanged shape)**:

| metric | value |
|--------|------:|
| latency_cycles | 8 532 189 |
| latency_ns | 34 129 000 |
| interval | 8 532 190 |
| bram | 32 |
| dsp | 3 |
| ff | 7 639 |
| lut | 5 799 |
| fmax_mhz | 313.09 |
| slack_ns | 0.806 |

**Pillar 1 feedback summary**:

```json
{
  "scope_count": 10,
  "loop_count": 5,
  "pipelined_loops": 4,
  "non_pipelined_loops": 1,
  "scopes_with_timing_violation": 2,
  "bottleneck_count": 6,
  "high_severity_bottlenecks": 2,
  "top_bottleneck_kinds": [
    ["ii_target_miss", 4],
    ["interval_exceeds_latency", 1],
    ["non_pipelined_hot_loop", 1]
  ]
}
```

**Top-3 bottlenecks emitted** (the actual agentic-decision input):

1. `[high] interval_exceeds_latency` on `workload` — interval 8 532 190 > latency 8 532 189 cycles. Top-level kernel cannot start a new transaction until the previous finishes (no dataflow / pipelining at module boundary).
2. `[high] non_pipelined_hot_loop` on `workload/L9` — trip=2048, latency=8.5M cycles, **not pipelined**. This is the dominant latency contributor and the obvious first target for the agent.
3. `[medium] ii_target_miss` on `workload/workload_Pipeline_L8/L8` — pipelined but achieved II=2, not II=1. Likely a memory-port conflict on the inner buffer access.

These are exactly the per-scope signals an agent needs to *decide what to optimize next* — which is the Pillar 1 contribution we set out to build. The same flow runs unchanged on any of the ~1600 ready-to-go kernels in the table above.
