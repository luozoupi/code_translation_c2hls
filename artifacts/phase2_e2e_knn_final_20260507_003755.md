## End-to-End Findings

Wall: 3888s static + 3986s dynamic = ~131 min total. Heavy host contention for the first ~21 min of each run (GT validation synth competing with another user's vpl/v++ workload). Per-step agentic synth runs were typically 15–30 s; per-step GT-comparison synths were 9–20 min each.

### What the static run showed
- **Phase 1's revert mechanism kept the trajectory honest**: 3 of 5 steps reverted (pipeline / unroll / doublebuffer) because they regressed against the just-improved tiling result.
- **Coalescing failed at the compile stage** twice (`ap_int.h` not found in the c2hls compile-check sandbox; the LLM didn't know to use the support tree). That's a Pillar 9 translation-failure-retry candidate (Phase 1 partially handles it, Phase 3 has a tighter retry payload ready in `robustness.translation_failure_retry_payload`).

### What the dynamic run showed
- **Phase 2 dynamic routing fired correctly**: step 1 was `coalescing` (matched `interval_exceeds_latency` → `prompt-coalescing` skill), step 2 was `doublebuffer`, then `tiling`, then a fall-back to static order for `pipeline` + `unroll`.
- **Pillar 9's no-op trap fired three times in production** (doublebuffer-retry, pipeline, pipeline-retry) — exactly the failure mode the smoke-test data documented in [`requested_agentic_hwemu_rerun_20260505_214545.jsonl`](../artifacts/requested_agentic_hwemu_rerun_20260505_214545.jsonl). The orchestrator surfaced these as `no_op_persisted` rather than silently committing them.
- **Pillar 9's throughput-regression check** flagged tiling (interval 4.01x growth) as a real regression in the gen-side metrics — distinct from "absorbed" or "no-op" cases.
- **Best PPA achieved was 524 753 cycles** (unroll step). Below baseline (2.0x) but still 2x off philip's reference best (262 480 cycles for coalescing on Vitis 2023.2 + U280).

### Phase 2 robustness layer in production: events fired
- `no_op` detections: 3 (doublebuffer-retry, pipeline, pipeline-retry on dynamic run)
- `throughput_regression`: 1 in dynamic-run live trajectory (tiling); the artifact's `Phase 2 verdict` blocks add the post-hoc retroactive count
- `trajectory_collapse_check`: not triggered — would fire on 3+ consecutive no-ops, dynamic run had at most 2 in a row

### Retroactive Phase 2 verdict on philip's reference (validation of calibration)
Applied to the **gold reference itself** without re-running anything:
- 4 events on a 6-step trajectory: 1 no-op (`pipeline` byte-identical to `tiling`), 3 throughput regressions (`tiling` +4.08x interval, `doublebuffer` interval 1.99x latency, `coalescing` interval 1.95x latency).
- The `pipeline` no-op is also visible in **philip's hw_emu data** (kernel_runtime_cycles 4 264 936 for both `tiling` and `pipeline`). The reference exhibits the exact failure modes our Phase 2 hooks were designed to catch.

### Phase 3 design ramp-up (built during this run, not yet exercised end-to-end here)
Phase 3 addresses two cognitive patterns the user identified:
1. **Trajectory-aware regression tolerance** ([`trajectory_alignment.py`](../trajectory_alignment.py)) — when the gen step regresses by ≈ the same factor the GT step regresses at the same position, KEEP the gen step (it's a structural enabler). Wired into [`run_optimization_step`](../c2hls.py) revert path. Smoke-tested with the canonical knn shape: a +4x latency tiling step that mirrors the GT's +4.08x ratio is now classified `enabling_regress` and not reverted.
2. **Combo-mode strategies** ([`prompt_c2hls.py`](../prompt_c2hls.py)) — three new step prompts: `combo_full` (apply ALL techniques in one rewrite), `combo_structural` + `combo_parallel` (2-step bundled). New `--strategy={static,dynamic,combo,combo_progressive}` CLI flag dispatches to the appropriate path in [`run_multistep`](../c2hls.py).

Phase 3 smoke test [phase3_smoke_20260507_000212.md](phase3_smoke_20260507_000212.md): **22/22 green**.

## Phase 4: FeedbackAgent (added after this run; refactor-only)

After this end-to-end run, a fourth LLM-call agent was added: a [FeedbackAgent](../c2hls.py) that consolidates the 7 feedback renderers (compile-error / synth-error / regression / no-op / alignment / throughput-regression / quality-gap) under one class, called via `self.feedback.render(kind, **kwargs)`. The change is a pure structural refactor — Phase 4 smoke test asserts byte-parity with the legacy free-function output. Sets the stage for an optional LLM-aided composition path (`compose_with_llm()`) that reads the LLM's actual edit when a deterministic template fails. Not exercised in this e2e run.

## combo_full follow-up run (Phase 3 single-shot, after Phase 4 wiring)

Re-ran the same kernel with `--strategy=combo_full --turns 4` after Phase 4 was wired in (a fresh Python process picked up Phase 3's combo prompts and Phase 4's FeedbackAgent). Wall: ~21 min total (most of it the GT validation re-synth, since combo_full only does one optimization step).

| step | success | effect | lat_cyc | latency_ns | ii | BRAM | DSP | FF | LUT | Fmax |

| combo_full | False | reverted | 3 278 989 | 17 519 000 | 3 278 990 | 37 | 6 | 8 891 | 7 645 | 187.16 |

Both combo attempts regressed (2.93x then 4.18x latency vs baseline). Reverted to baseline. Phase 1's regression-revert mechanism saved the trajectory from a bad combined rewrite. **Finding**: on a small kernel where the LLM's baseline translation was already efficient (1.05M cycles ≈ philip's 1.05M reference baseline), asking Haiku to apply *all five techniques in one rewrite* produced a structurally different kernel (very different LUT/FF profile) that synth'd 3.1x slower. The cognitive pattern is real, but combo_full is too aggressive for small kernels where the baseline is already a near-final design point.

**Single-kernel takeaway**: dynamic routing produced the best on-device PPA on knn under Haiku 4.5 in this run. Static and combo_full both failed to improve materially after baseline. This is one kernel — generalization needs more benchmarks (Pillar 8 dataset rollout).
