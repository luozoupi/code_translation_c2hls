GLOBAL SKILL LIBRARY — all applicable optimization recipes plus avoid rules (same set for every kernel on PC2). Pattern → strategy → required steps → guardrails → template/example for the `flash` step:

[skill hls-baseline-load-compute-store-gate] confidence=high pass=0/0
  kind: compound_transformation
  pattern: kernel has m_axi or global array arguments and the hot loop reads or writes those arrays directly
  strategy: before any tiling, unrolling, coalescing, or DATAFLOW: separate into bulk load, pipelined local compute, and bulk store; never leave the hot compute loop on global or m_axi memory
  required steps:
    - identify all array parameters accessed in the hot loop
    - estimate compile-time working-set size (inputs + outputs + temporaries)
    - if working set fits on-chip BRAM budget, stage full arrays locally in one load pass
    - else choose tiling with reuse analysis, not a default small tile size
    - add #pragma HLS PIPELINE II=1 to every dedicated load and store loop
    - add #pragma HLS PIPELINE II=1 to the local-memory compute loop when legal
    - verify compute indexing uses local buffers, not global array parameters
    - before submitting, confirm the kernel body contains PIPELINE pragmas on every major compute phase; zero PIPELINE on compute is a blocking defect
    - only after this baseline is in place, apply advanced skills (tiling, unroll, coalescing)
  guards:
    - do not stage unbounded or runtime-sized arrays entirely on-chip
    - do not skip local staging because m_axi pragmas are already present
    - do not apply advanced optimizations on top of a reference port that still reads globals in compute
  template/example:
    double local_in[M][N], local_out[M][N];
    load: for (int i = 0; i < M; i++)
      for (int j = 0; j < N; j++) {
    #pragma HLS PIPELINE II=1
        local_in[i][j] = in[i][j];
      }
    compute: for (int i = 0; i < M; i++)
      for (int j = 0; j < N; j++) {
    #pragma HLS PIPELINE II=1
        local_out[i][j] = f(local_in, i, j);
      }
    store: for (int i = 0; i < M; i++)
      for (int j = 0; j < N; j++) {
    #pragma HLS PIPELINE II=1
        out[i][j] = local_out[i][j];
      }
[skill axi-burst-coalescing-narrow-safe] confidence=high pass=1/5
  kind: compound_transformation
  pattern: m_axi port feeds a contiguous streaming loop, the active host/testbench contract expects the original scalar pointer types, and memory bandwidth limits performance
  strategy: preserve the public scalar pointer ABI; request 512-bit automatic m_axi widening with max_widen_bitwidth=512; use burst/outstanding pragmas; stage contiguous data into local buffers; pipeline load/store loops; and rewrite the compute loop to process LANES = 512 / element_bitwidth elements per memory beat when iterations are independent
  required steps:
    - add max_widen_bitwidth=512 to relevant m_axi ports
    - use burst length and outstanding transaction pragmas
    - stage contiguous global-memory regions into local buffers where helpful
    - compute LANES = 512 / element_bitwidth
    - rewrite the compute loop to process multiple lanes per outer iteration when legal
    - partition local lane buffers to match the lane factor
    - validate csim/cosim and inspect synthesis reports for burst/widening success
  guards:
    - do not change top-level pointer element types unless explicitly allowed
    - do not treat adding m_axi pragmas as complete coalescing
    - confirm accesses are contiguous and burst-friendly
    - only unroll lane computation when iterations are independent or safely reducible
    - handle N not divisible by the lane factor
  template/example:
    #pragma HLS INTERFACE m_axi port=in  offset=slave bundle=gmem max_widen_bitwidth=512 max_read_burst_length=64 num_read_outstanding=16
    #pragma HLS INTERFACE m_axi port=out offset=slave bundle=gmem max_widen_bitwidth=512 max_write_burst_length=64 num_write_outstanding=16
    // Keep pointer element types unchanged unless the active variant explicitly allows a packed wide-bus ABI.
    // After widening, restructure computation around LANES = 512 / element_bitwidth when legal.
[skill hls-doublebuffer-dataflow-stage-split] confidence=high pass=0/0
  kind: supporting_transformation
  pattern: load, compute, and store logic is mixed in a single loop or function, preventing DATAFLOW scheduling or stage overlap
  strategy: split the code into explicit producer/consumer stages connected by local buffers or streams, then apply DATAFLOW at the parent scope when dependencies allow
  required steps:
    - extract load stage
    - extract compute stage
    - extract store stage
    - define buffer or stream interfaces between stages
    - ensure no hidden cross-stage dependence prevents overlap
    - apply DATAFLOW at parent scope
    - check dataflow report for actual concurrency
  guards:
    - do not use DATAFLOW if stages are still sequentially dependent on the same buffer instance
    - do not create streams without bounded production/consumption behavior
    - avoid deadlock-prone stream cycles
  template/example:
    #pragma HLS DATAFLOW
    load_stage(in, load_to_compute);
    compute_stage(load_to_compute, compute_to_store);
    store_stage(compute_to_store, out);
[skill prompt-doublebuffer] confidence=high pass=1/1
  kind: compound_transformation
  pattern: load, compute, and/or store phases operate on consecutive chunks or tiles but currently execute serially with no overlap
  strategy: create ping-pong local buffers and a legal producer/consumer schedule so load of tile k+1 overlaps compute of tile k and optionally store of tile k-1
  required steps:
    - split load, compute, and store into separable stages
    - allocate two or more local buffers for ping-pong scheduling
    - use tile index parity to alternate buffers
    - guard first and last iterations
    - apply DATAFLOW only when dependencies allow overlap
    - validate that phases overlap and local memory usage remains acceptable
  guards:
    - do not add two buffers if phases still execute serially
    - do not use DATAFLOW when stage dependencies prevent overlap
    - avoid double buffering if local memory usage becomes excessive
    - preserve first-tile and last-tile behavior
  template/example:
    #pragma HLS DATAFLOW
     for (int t = 0; t < NUM_TILES + 1; ++t) {
        if (t < NUM_TILES) load_tile(in, buf[t & 1], t);
        if (t > 0) compute_tile(buf[(t - 1) & 1], out, t - 1);
    }
[skill hls-doublebuffer-load-compute-store] confidence=high pass=0/0
  kind: compound_transformation
  pattern: the kernel processes data in chunks or tiles, and load, compute, and store phases for consecutive chunks currently execute serially
  strategy: split the design into load, compute, and store stages; allocate ping-pong buffers; overlap load of tile k+1, compute of tile k, and optionally store of tile k-1
  required steps:
    - identify chunk/tile loop
    - split load, compute, and store stages
    - create at least two local buffers per overlapped data stream
    - alternate buffers using tile index parity
    - handle prologue and epilogue iterations
    - apply DATAFLOW if stages have legal producer/consumer dependencies
    - validate functional correctness and actual phase overlap
  guards:
    - do not add ping-pong buffers unless overlap is possible
    - avoid excessive local memory use
    - preserve first and last tile behavior
    - avoid read/write hazards between buffers
  template/example:
    #pragma HLS DATAFLOW
     for (int t = 0; t < NUM_TILES + 2; ++t) {
        if (t < NUM_TILES) load_tile(in, in_buf[t & 1], t);
        if (t > 0 && t <= NUM_TILES) compute_tile(in_buf[(t - 1) & 1], out_buf[(t - 1) & 1], t - 1);
        if (t > 1) store_tile(out_buf[(t - 2) & 1], out, t - 2);
    }

[skill hls-avoid-zero-pipeline-submit] confidence=avoid pass=0/0
  kind: avoid_rule
  pattern: the proposed kernel body has no #pragma HLS PIPELINE on any compute loop, or the only pragmas are m_axi or s_axilite interface pragmas
  strategy: never submit a kernel whose hot loops lack PIPELINE pragmas; apply the baseline load-compute-store gate first even when avoid rules discourage advanced transforms
  required steps:
    - scan the kernel body for #pragma HLS PIPELINE on compute loops
    - if none are present, reject the output as a reference port
    - route to hls-baseline-load-compute-store-gate and hls-multi-phase-local-pipeline
    - add pipelined load, local compute, and store loops before resubmitting
  guards:
    - m_axi interface pragmas alone are not an optimized kernel
    - a flash output with only interface pragmas will synthesize as unpipelined scalar hardware
    - uncertainty about advanced optimizations does not justify skipping the baseline gate

[skill hls-multi-phase-local-pipeline] confidence=high pass=0/0
  kind: compound_transformation
  pattern: the kernel contains multiple sequential loop nests or update phases over matrices and vectors exposed as m_axi arguments, and one or more phases still read or write those arguments directly in the hot loops
  strategy: for multi-phase kernels, bulk-load shared inputs to locals, execute every phase as pipelined local-memory compute with flattened static nests where applicable, and bulk-store final outputs once; never emit a reference-style multi-loop port on global memory.
  required steps:
    - list all phases and the arrays each phase reads or writes
    - load every array touched by more than one phase into local buffers once
    - rewrite each phase to use only local buffers with pipelined loops
    - apply hls-chain-intermediate-results-locally when later phases consume earlier outputs
    - store only final results that must be visible off-chip
    - add array_partition on local arrays accessed in parallel inner loops
    - for each GEMM-like phase, require flatten of (i,j) and k-dim partition; fail the design if any phase keeps outer i sequential
  guards:
    - m_axi pragmas on many ports do not remove the need for local staging
    - each phase still needs pipelined loops over local data
    - do not leave any phase as a scalar nest on global arrays
  template/example:
    load all shared arrays to locals;
    phase1: for (i) for (j) { #pragma HLS PIPELINE II=1
    #pragma HLS LOOP_FLATTEN ... local only, k UNROLL ... }
    phase2: same flatten pattern on locals;
    store final outputs once;
[skill hls-iterative-stencil-timestep-local-volume] confidence=high pass=0/0
  kind: compound_transformation
  pattern: an outer time-step or iteration loop performs a 2D or 3D neighbor stencil that reads and writes grid values, and the current code accesses global or m_axi arrays inside the time-step loop
  strategy: for iterative stencils, keep the working volume on-chip across time steps using full-grid local buffers or old/new planes; never leave the time-step loop on global memory
  required steps:
    - load the full grid or each needed volume into local memory once before the time-step loop
    - allocate two local buffers for old/new state when the stencil alternates between two arrays
    - perform all neighbor reads from local buffers inside the time-step loop
    - pipeline the innermost legal traversal loop with II=1
    - swap or copy old/new buffers between time steps without global round-trips
    - store the final volume once after all time steps
  guards:
    - do not perform global load/store inside the time-step loop when the full volume fits on-chip
    - use old/new local volumes or planes rather than per-tile global round-trips each timestep
    - hardcoding trip counts instead of using compile-time constants is a separate defect
  template/example:
    double local_A[2][N][N][N];
    load_volume_once(...);
    for (int t = 1; t <= TSTEPS; t++) {
      compute_into_local_B_from_local_A(...);
      compute_into_local_A_from_local_B(...);
    }
    store_volume_once(...);
[skill hls-chained-gemm-local-temporary] confidence=high pass=0/0
  kind: compound_transformation
  pattern: the kernel chains two or more matrix multiplies or GEMM-like phases where a temporary array is written in one phase and read in the next phase, and the temporary is currently written to global memory between phases
  strategy: never chain GEMM phases through global memory; keep the temporary in a local buffer across phases and pipeline both multiplies on-chip. For each GEMM phase with static bounds: partition locals on the reduction (k) dimension, PIPELINE II=1 the (i,j) nest with k fully unrolled, and require nest flatten so outer i is not left sequential.
  required steps:
    - identify the temporary array produced by phase 1 and consumed by phase 2
    - allocate a local buffer for the temporary with the same compile-time dimensions
    - partition A/B/tmp/C locals on the k (reduction) access dimension — required when k is fully unrolled
    - run each GEMM phase with PIPELINE II=1 on (i,j), UNROLL on k, and LOOP_FLATTEN (or a single ij loop)
    - verify each phase reports one flattened pipeline over ~M*N trips, not sequential outer i
    - if phase2 flattened and phase1 did not, mirror phase2's partition+flatten onto phase1
    - store the temporary to its global port only once if the ABI requires it
  guards:
    - apply even when the temporary array is also an m_axi output port
    - preserve the external ABI by storing the local temporary once after all consuming phases complete
    - reject a phase whose csynth loop table shows compute_* outer trip=M, II=-, Pipelined=no while an inner j claims II=1
    - if one GEMM phase flattened and a sibling did not, copy the successful partition+flatten pattern onto the slow phase
  template/example:
    double local_tmp[M][N], local_A[M][K], local_B[K][N], local_C[N][P], local_D[M][P];
    #pragma HLS ARRAY_PARTITION variable=local_A complete dim=2
    #pragma HLS ARRAY_PARTITION variable=local_B complete dim=1
    #pragma HLS ARRAY_PARTITION variable=local_tmp complete dim=2
    // phase1: local_tmp = alpha * A * B
    compute_tmp: for (int i = 0; i < M; ++i) {
      for (int j = 0; j < N; ++j) {
    #pragma HLS PIPELINE II=1
    #pragma HLS LOOP_FLATTEN
        double sum = 0.0;
        for (int k = 0; k < K; ++k) {
    #pragma HLS UNROLL
          sum += alpha * local_A[i][k] * local_B[k][j];
        }
        local_tmp[i][j] = sum;
      }
    ...
[skill hls-chain-intermediate-results-locally] confidence=high pass=0/0
  kind: compound_transformation
  pattern: the kernel has multiple dependent compute phases where an intermediate array produced in one phase is consumed by a later phase, and the current design writes that intermediate to global memory between phases
  strategy: keep every intermediate result that is consumed by a later phase in on-chip local memory; chain phases locally and defer global writes until the value is no longer needed
  required steps:
    - identify arrays written in one phase and read in a later phase
    - allocate local buffers for each reused intermediate result
    - run phase 1 compute into local intermediate buffers
    - run later phases using only local intermediates
    - partition or bank local buffers to match inner-loop unroll factor
    - store only final outputs that are not consumed again
    - pipeline load, each local phase, and final store
    - for matrix-multiply phases, flatten (i,j) and partition on k; do not leave sibling phases with mismatched flatten
  guards:
    - do not spill an intermediate consumed by the next phase if it fits in on-chip memory
    - preserve producer-consumer ordering between phases
    - only write final outputs or arrays not reused later to global memory
  template/example:
    double local_A[M][K], local_B[K][N], local_E[M][N], local_F[N][P], local_G[M][P];
    // load inputs once
    // phase1: local_E = local_A * local_B
    // phase2: local_F = ...
    // phase3: local_G = local_E * local_F
    // store local_G once
[skill hls-multi-pass-stats-local-staging] confidence=high pass=0/0
  kind: compound_transformation
  pattern: the kernel performs multiple passes over the same dataset (reduction, normalization, pairwise aggregation, correlation, covariance, or similar) with repeated global reads and writes of the main data array between passes
  strategy: stage the main data array locally, run every statistics or normalization pass on local memory with pipelined loops, and minimize repeated global traversals of the same array
  required steps:
    - identify all passes that traverse the same main data array
    - if the dataset fits on-chip, load it into a local buffer once
    - compute mean, variance, normalization, and aggregation passes over the local buffer with pipelined loops
    - keep small statistic vectors in local memory
    - write normalized data and final output matrix back in dedicated store loops
    - avoid leaving hot passes as unpipelined scalar loops on global memory
  guards:
    - statistics vectors such as mean and stddev should also be computed and stored locally when small
    - preserve numerical semantics of each pass
    - pipeline each pass separately; do not reread the full dataset from global memory every pass if it fits locally
  template/example:
    double local_data[ROWS][COLS];
    load_data: for (...) { #pragma HLS PIPELINE II=1 local_data[i][j] = data[i][j]; }
    pass_mean: for (...) { #pragma HLS PIPELINE II=1 ... local_data / local_mean ... }
    pass_norm: for (...) { #pragma HLS PIPELINE II=1 ... local_data ... }
    store_outputs: for (...) { #pragma HLS PIPELINE II=1 ... }
[skill hls-prefer-full-workspace-staging-when-fits] confidence=high pass=0/0
  kind: supporting_transformation
  pattern: compile-time array dimensions are bounded and total working set (all inputs, outputs, and needed temporaries) fits available on-chip memory without tiling
  strategy: load the full working set into local arrays once, run all compute on local memory, store once; do not default to nested small-tile loops that repeatedly reload the same global data. After staging, GEMM/matmul compute nests must still be flattened with k-dim partition — staging alone does not fix outer-i sequential latency.
  required steps:
    - sum element counts times sizeof for each array needed during compute
    - compare against conservative BRAM budget for the target FPGA
    - if it fits, allocate local arrays matching problem dimensions and use bulk load, compute, and store

  guards:
    - do not allocate local arrays larger than synthesis can map
    - if full staging does not fit, increase tile size based on reuse and BRAM, not a fixed small constant
  template/example:
    double local_A[M][K], local_B[K][N], local_C[M][N];
    #pragma HLS ARRAY_PARTITION variable=local_A complete dim=2
    #pragma HLS ARRAY_PARTITION variable=local_B complete dim=1
    load_arrays: for (int i = 0; i < M; i++)
      for (int j = 0; j < K; j++) {
    #pragma HLS PIPELINE II=1
        local_A[i][j] = A[i][j];
      }
    // repeat for B (and C if needed), then flattened local compute, then one store pass
